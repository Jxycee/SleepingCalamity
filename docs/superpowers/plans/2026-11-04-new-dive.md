# The New Dive Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire plan 1's pure dive rules and plan 2's per-player bags into the live game, so a party can play the Undercroft end to end: church trapdoor, floors 1-7, the halfway bank room with its push-on or go-home choice, the one-time checkpoint and floor pick, stir per half, failure with a lost satchel, and a stand-in ending after floor 7.

**Architecture:**
- One new Core class, `DiveSession`, owns the host's dive rules (floor, phase, `DiveStir`, `DiveMomentum`, `BossRetry`, the pieces). `PartyBags` and `DiveCheckpoint` outlive a dive: the director owns them and passes them to each fresh `DiveSession` (Task 2 constructor). It replaces `DiveState`, `DiveRoute`, `StirMeter` and `StirTuning`. `DiveHaulSync` and `DiveDirector` stay the net shell around it.
- Floors come from a `DiveFloorTable` over `UndercroftPlan`: floors 2, 4, 6, 7 come from the existing generator, and floors 1, 3, 5 are hand-placed stand-ins built with the generator's `PlaceFixed`/`LinkFixed`. Phase 1 has no water gimmick and no new rooms.
- Pieces and people use `PieceDepths.Assign` (table in decision 10) and are saved in the world save. The bank room, the satchel on its floor, gold and boots are host-authoritative and per player. The bank push-on writes a `suspend` save section (per-player bag state, decision 9) that a later load resumes at floor 6; stair save-and-quit reuses it in a later plan.
- Piece state between tasks: Task 5 adds `DivePieces` beside `DiveHaul`; Task 7 moves the live readers (`DiveHaulSync`, `CellarContentsSync`, `DiveDirector`) to `DiveSession.Pieces`; Task 12 moves the last callers (`TownStock.Receive`, `TownSaves.RestoreHaul`, the old tests) and deletes `DiveHaul`.

**Tech Stack:** C# 9 (Unity 6000.6.5f1), NGO 2.13, Newtonsoft JSON (world save), NUnit 3, `Pcg32` + `Rng.Derive` (`Core/Random`).

**Spec:** `docs/superpowers/specs/2026-11-03-hearthdeep-dungeon-design.md`: decisions 2-8, 13, 18-21, 23, 26-28, 31-39, 44, 46-47; sections 4.1-4.5, 4.8, 5, 12 steps 1 and 3. Roadmap row 3 of `docs/superpowers/plans/2026-11-03-dive-build-roadmap.md`. Builds on plan 1 (`UndercroftPlan`, `DiveStir`, `DiveMomentum`, `BossRetry`, `DiveCheckpoint`, `BankSlots`, `LostSatchel`/`SatchelSlot`, `PieceDepths`, `BreadLadder`) and plan 2 (`PlayerBag`, `PartyBags`, `DiveHaulSync` bags, `PlayerBagSync`, `BagsSave`).

## Global Constraints
- Host-authoritative. Only the host writes `NetworkVariable`s; clients ask by RPC and the host re-checks every rule. Every networked class keeps a class-level `// Authority:` comment (`sc-netcode`). No anti-cheat beyond normal host validation.
- Core stays pure C# with no `UnityEngine`. Core test files use only `System*`, `NUnit*`, `SleepingCalamity.Core*`, so `python Tools/cloud/sc_core_tests.py` runs them on the PC without Unity.
- World save (`sc-netcode`): every new state is an optional v1 section or field, cleaned on its own, with its row in `WorldSaveStore.Prepare`'s `Sections` table. A bad value drops only that entry. The golden v1 fixture passes unchanged. A `WorldSaveStoreTests` round trip and a "bad value keeps the rest" case per section. PlayMode save tests use `WorldSaveStore.PathOverrideForTests`.
- Every new Core class that crosses the network or the save gets an `// Authority:` comment line in the style of `PartyBags.cs` ("Authority: host only (...)"). Every networked or saved task states a `Catches:` line (what its tests do and do not prove).
- Restores never fire toasts. One-shots are RPCs and never replay on late join.
- Never edit `.prefab`/`.unity` YAML; builders write them (`build` run, commit the output). New `.cs` files get Unity-made `.meta` files from the task's `gate` run; never hand-write GUIDs.
- Every new number is a `public const` marked *placeholder*.
- Fresh floors every dive; found pieces and people stay found; a piece is safe the moment it is picked up. Bread, pieces, people and keys are never banked and never lost on failure.
- Keys, pieces and people stay one shared host-held copy. Loot, gold, bank slots, momentum rolls and the satchel are per player (decision 39).
- Tier-1 enemies only; at most 8 live enemies with four players. Phase 1 adds no new enemy, room or art.
- Seeds: `uint` dive seed, `ulong` world seed. A floor depends only on `(seed, floor)`.
- After merging `origin/main`, re-pin any moved golden from the failure message. Known: rooms-v2 moves `CellarLootMixTests.LootMixHash_Golden_Seed12345` and the seed-12345 floor 1-3 goldens; Task 3 moves the floor 4+ goldens.
- Test commands (PC): Core: `python Tools/cloud/sc_core_tests.py --where "class =~ <TestClass>"`. Gate: `powershell -NoProfile -ExecutionPolicy Bypass -File C:\Dev\SleepingCalamity\.claude\worktrees\magical-liskov-576bbe\Tools\unity.ps1 gate -OutDir <scratch>`. PlayMode: same wrapper `test-play -Filter <regex>`; run the PlayMode guard first and check `SC MARKER` equals HEAD. Full `check` only before the merge into main.
- Leave `CURRENT.md` alone. Branch `claude/plan3-plan` is the plan's branch; the implementing session works on its own branch and commits after each task.

## Review Focus
1. **A party pushes on still carrying valuables.** Four players with 10 valuables each must not re-latch extra enemies or the hunter at push-on, and reward must not count the valuables twice. Test: Task 1, `PushOn_WithValuablesCarried_DoesNotRelatch`.
2. **Wipe, rejoin, or quit at the bank.** A failure at floor 7 leaves one satchel per player at depth 7; a second failure replaces an unrecovered satchel; quitting at the bank restores carried items, bank state, stir and momentum without becoming a failure. Tests: Task 2 `Fail_AfterPushOn_StartsAtFloor1`, Task 6 `Suspend_RoundTrip_KeepsCarriedAndBankState`, Task 8a `LoadedSuspend_ResumesAtFloor6_WithStirMomentumAndBags`.
3. **The party shrinks or grows while the bank room is open.** Capacity follows who is present; excess picks drop from the end; a rejoiner gets a visit; the 3-player extra slot is never the previous owner, also across a restart. Tests: Task 8.
4. **Checkpoint edge cases.** Holding it and picking floor 3, picking floor 1, being at the boss shortcut with no checkpoint, an old save with no checkpoint field. Tests: Task 2 `TryStart_*`, Task 6 `OldSave_NoCheckpointField_ReadsAsNotHeld`.
5. **Retired code and old saves.** A 4-floor save (`ClearedMask` bits 1-4, `CheckpointReached` floor-2 checkpoint, banked loot) loads into the new dive without losing pieces, people or stash. Test: Task 12 `OldFourFloorSave_LoadsIntoNewDive`.

## Decisions this plan takes (the spec is silent or ambiguous; recorded here)
1. **Push-on and valuables (dive-rules review).** `DiveStir.OnPushOn` records a baseline of the valuables still carried, and only valuables above the baseline stir the second half. The carried ones enter `RewardValue` once, through `_rewardCarry`. Reward is capped at 100, so `RewardRankBonus` tops out at 2 (placeholder; a half that ends at 100 gives the second half no extra reward).
2. **"Start at the bank" (decision 31) = the bank room on floor 5**, with the guardian already beaten; the party arrives at the bank room's entrance. Picking floor 5 as the checkpoint start therefore skips the Ox fight (*proposal*; the spec's "bank" and "floor 5 set piece" are the same floor).
3. **Floor 5 is a stand-in:** the Dough Warden stands in for the Brazen Ox (no retry, decision 32); the innkeeper is a flag, not a character. Floor 3 reuses the bakery maze (`CellarBakeryPool`, now at floor 3) with the baker on it. The Brazen Ox, the water gimmick and the real set pieces are later plans.
4. **Gold source (none exists):** a chest roll can be a gold purse (*placeholder*, one in four rolls, per player). Enemy drops stay unbuilt.
5. **Gear is bankable** (`BankSlots.IsBankable`), because the Phase 1 bankable class is boots (spec section 5). Boots: `DiveItemKind.Gear`, +5% run and sprint speed, never jump distance; one pair per player.
6. **A chest opened with a full bag is refused** (stays closed for that player, toast "bag full"). The satchel counts as one of the carried slots.
7. **Bank capacity follows presence** while the room is open (parked item: visit under capacity).
8. **Save at the bank** writes the new `suspend` section, with bags saved as carried (not as failed, unlike a mid-dive quit). Stair save-and-quit uses the same section in a later plan.
9. **Suspend and resume (*proposal*).** The `suspend` section holds, per recorded player, a full mid-dive bag record (carried items, banked-this-dive, dive gold, opened-chest mask and its seed/floor, carried satchel, picks). A save with a `suspend` section loads as "in the bank room, push-on not yet chosen or already chosen": the party resumes at the start of floor 6 with the saved stir, momentum, retry and bank state, floor 5 treated as cleared, bank locked. Using the section clears it. A suspended save is never counted as a failed dive. Quitting in the bank room BEFORE push-on is the normal save-and-quit (spec 4.6): it writes the same section with `PushedOn == false`, and the load puts the party back in the bank room (visits reopened). Quitting on floors other than the bank room keeps today's failed-dive rule.
10. **Piece table (*proposal*).** Ids stay as saved (100, 101, 200, 201, 300, 301, baker 400) so old saves keep their pieces, but the id no longer encodes a floor. `PieceCatalog.Specs` (a `PieceSpec` table, `PieceDepths` already has the struct): 100 frame, random first half; 101 oven, random first half; 200 door, random first half; 201 sign, random first half; 300 spare frame and 301 spare oven, random second half; 400 baker, fixed floor 3. First-half random candidates are floors 2 and 4 only (floor 1 excluded, 3 and 5 are set pieces), so one floor can hold up to four pieces: `CellarPieceSpots` must give four spots and a test pins it. Second-half candidates are floors 6 and 7. Depths are assigned once at world creation (and for an old save with no `PieceDepths` field, at first load) from the world seed, written to the save, never recomputed. `DiveHaul.PieceId(floor, index)` has no replacement: callers use the id constants in `PieceCatalog`.
11. **Confirm window for push-on / go home (*proposal needing user sign-off*; the spec says only that the bank choice is shared).** Any present, living player's press opens a 10 s *placeholder* window; a second player's press for the same choice, or the timer, confirms; solo is instant; a press for the other choice swaps the window. Downed or absent players are not counted in the quorum (quorum = living present players, at least 1).
12. **Boots (*proposal*).** Boots are worn automatically, one pair per player (a second pair is refused as a duplicate). The +5% applies while the boots id is in the player's carried list, banked-this-dive list or home stash (so it applies as soon as picked up and after the bank; a lost satchel with boots removes it until recovered). The multiplier is read owner-side (`MovementMath.RunSpeed` is a `const`), stays client-predicted, and has no host check (no anti-cheat).
13. **Roll order for boots (*proposal*).** `RollFor(..., rankBonus)` stays identical to today for `rankBonus == 0`. Boots are not folded into the rank draw: a separate boots roll from its own stream (`cellars.loot.boots`) replaces the item only when the first roll lands on a band that allows gear; momentum's rank bonus does not touch it. This keeps every existing seed's picks and the loot-mix golden unchanged (floors 6-7 triple the boots roll chance, *placeholder*).
14. **Gold purse (*proposal*).** `CellarLoot.GoldId` is a negative sentinel. `PlayerBag.Add` rejects ids <= 0 on purpose, so `CellarContentsSync` (chest open) diverts a purse roll to `ServerAddGold` before it ever calls `Add`.
15. **Innkeeper** stays a flag only; the innkeeper character flag deferral is in the table.
